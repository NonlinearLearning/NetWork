# 协议层设计

## 目标

协议层负责描述“一个包长什么样”，并提供统一的读、写、校验过程。

这一层的重点不是业务逻辑，而是把协议事实冻结成稳定 schema。

## 核心组成

### `PacketDefinitionBuilder<TPacket>`

定义期收集器，用来逐步声明一个包的结构。

- 可以声明普通字段、`BitsByte`、自定义字段和字段组
- 为每个字段分配稳定顺序
- 通过 `Build()` 一次性冻结定义

这意味着：

- 定义期可变
- 运行期只读
- 避免 schema 在注册后继续被外部修改

### `PacketFieldHandle`

字段句柄用于在定义层引用字段，而不是依赖裸字符串。

它主要解决两个问题：

- 条件依赖引用真实字段节点
- 依赖关系可以在建模阶段做静态检查

### `PacketCondition`

条件用于描述字段何时出现。

当前支持两类主要入口：

- `PacketCondition.Create(...)`
  - 通用条件表达
- `PacketCondition.Flag(...)`
  - 适配旧协议里“某个 flag bit 决定字段是否出现”的常见模式

条件会记录依赖字段句柄，因此定义层可以验证：

- 条件依赖的字段必须存在
- 条件只能依赖前序字段，不能依赖未来字段

### `PacketFieldGroupDefinition`

字段组用于表达“一个控制位对应多个字段”的协议模式。

它同时负责：

- 共享条件
- 组存在性判断
- 组内一致性判断

这对 `13` 号包中一个控制位控制多个字段的情况是必要的。

## 冻结后的定义

`PacketDefinition<TPacket>` 是 `Build()` 的最终产物。

它保存：

- `MessageId`
- `FlagBytes`
- `Fields`
- `FieldGroups`
- `CustomCodec`

在构造时会立即执行定义层校验，尽早拦截：

- 重复字段名
- 条件依赖未知字段
- 条件依赖后序字段
- 字段组引用未知字段

## 编解码流程

### 写入

`PacketCodec.Write(...)` 的默认流程是：

1. 校验字段和字段组一致性
2. 写入 `messageId`
3. 按字段顺序写入 payload
4. 跳过条件不满足的字段

### 读取

`PacketCodec.Read(...)` 的默认流程是：

1. 先读取并校验 `messageId`
2. 创建空包对象
3. 按字段顺序读取 payload
4. 确保字节被完整消费
5. 执行读后校验

### 校验

`PacketCodec.Validate(...)` 负责：

- 字段存在性和条件匹配校验
- 字段组一致性校验
- 包级附加规则校验

## `CustomCodec` 的定位

`IPacketCustomCodec<TPacket>` 是复杂包的逃生口。

它允许少数无法用默认字段引擎表达的包自行实现：

- `Write`
- `Read`
- `ValidatePacket`

当前设计仍然把它视为例外机制，而不是主路径。

## 注册表设计

`PacketDefinitionRegistry` 提供两类映射：

- `messageId -> reader`
- `packet type -> writer`

对外暴露两个统一入口：

- `Read(NetMessage message)`
- `Write(object message)`

这让上层运行时不需要知道某个具体包的 codec 细节，只需依赖注册表。
