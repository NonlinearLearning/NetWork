# 数据包有向依赖图初步提案

> 当前实现入口：`Prototypes/graph-layout-codegen/`。本文保留依赖图设计结论；文中的旧 `Concept/` 路径已按迁移后的语义原型路径更新。

## 决策

`Prototypes/graph-layout-codegen/src/test1/` 先只实现一个不可变的静态定义图。一个包的所有普通字段和变长字段都是 `PacketNode`；字段之间的结构性前置关系是 `PacketEdge`。不再保留 `IPacketRelation`、`PacketRelation`、抽象节点层或 `When` 回调。

```csharp
var controlFlags2 = PacketNode.Field<PlayerControlsPacket13>(packet => packet.ControlFlags2);
var velocity = PacketNode.Variable<PlayerControlsPacket13>(packet => packet.Velocity);

var definition = new PacketDefinitionGraph(
    [controlFlags2, velocity],
    [new PacketEdge(controlFlags2, velocity, PacketEdgeType.Presence)]);
```

边的方向固定为 **前置节点 -> 被影响节点**。上例表示 `ControlFlags2` 决定 `Velocity` 是否存在。

## 最小模型

| 类型 | 责任 | 不承担的责任 |
| --- | --- | --- |
| `PacketNode` | 由真实字段或属性表达式冻结 `OwnerType`、`Name`、`ValueType` 与 `Kind`；可选地持有该字段的 binary reader/writer | 不保存 `MemberInfo`、本次收发包的值，也不决定字段顺序或条件范围 |
| `PacketEdge` | 直接保存 `Source`、`Target` 和依赖类型 | 不再包一层 relation 对象 |
| `PacketDefinitionGraph` | 验证节点、边和无环性；保留声明顺序 | 不改变 wire 顺序，不执行 codec |

`PacketNodeKind` 暂时只有：

- `Field`：一个固定形态的字段。
- `Variable`：长度、元素数或实际编码形态受前置字段影响的字段。

`PacketEdgeType` 暂时只有：

- `Presence`：源节点决定目标节点是否出现在 wire 中。
- `Shape`：源节点决定目标节点的长度、项数或编码形态。
- `Constraint`：源节点是目标节点合法性的前置输入；具体校验规则仍由 codec 层负责。

这是分类标签，不是可执行的条件语言。复杂的布尔表达式、选择分支、RLE 状态和业务校验在有真实包需要时再引入，并且必须有能表达其语义的测试；不能用一个空泛接口提前占位。

## 构造与校验

`PacketDefinitionGraph` 在构造时接收完整节点和边集合，并复制为只读视图。它必须拒绝：

1. 非字段/属性成员、索引属性或重复的节点名称；
2. 端点不属于本定义的边；
3. 自环与任意长度的有向环；
4. 未定义的边类型。

节点集合的输入顺序就是静态 wire 声明顺序。图的拓扑关系只用于确认“读取目标前，前置值已经可得”，绝不重排字段。这样 `Packet 13` 的固定线序和条件字段线序仍可直接阅读。

## 与序列化和校验的关系

该图不是第二套序列化系统。后续 `PacketFramework` 的字段定义仍拥有 codec；它只需引用同名或同一实例的节点。读、写和结构校验应查询同一份边：

```text
读：先读取 Source，按 EdgeType 决定 Target 是否/如何读取
写：先投影 Source，按同一 EdgeType 决定 Target 是否/如何写入
校验：确认 Target 的存在性或形态与 Source 一致
```

第一阶段只落地图的声明与定义期校验，不把 lambda、值槽、DTO 或运行期状态塞入图中。这样可以先稳定依赖模型和可读输出，再以真实 Packet 13、WorldData、TileSection 的测试决定下一种必要结构。

### 已落地的简单包样例：PlayerActive（14）

原版 `NetMessage` 写入 `PlayerId`、`ActiveFlag` 两个 byte，`MessageBuffer` 以同一顺序读取。`Prototypes/graph-layout-codegen/src/test1/PlayerActivePacket14GraphConcept.cs` 用两个直接成员表达式声明 `PlayerActivePacket` 的属性；工厂只在建图时解析表达式，并将包类型、成员名称和值类型冻结到节点中。它构造一个没有依赖边的图，并在概念层按该固定顺序读写。

```text
14 | PlayerId | ActiveFlag
```

`PlayerActivePacket14GraphConcept` 同时公开 `PacketType.PlayerActive` 和 `Graph`，并在读写前确认 DTO 非空、message id 与固定长度正确。它是简单包的概念基线，尚未接入正式 `PacketFramework`；条件、变长和分支包不能假装成这个模型。

### 已落地的依赖包样例：PlayerControls（13）

`Prototypes/graph-layout-codegen/src/test1/PlayerControlsPacket13GraphConcept.cs` 现在以一个 `PacketLayout<PlayerControlsPacket13>` 声明全部 12 个 wire 字段：`PlayerId`、四个控制字节、固定字段，以及五个条件字段。`PacketLayout` 本身就是顺序的扁平字段列表；条件直接附着到目标字段，并由 `PacketFlagBitCondition` 指向控制字节的某一位。`Graph` 不再手写，而是从这份扁平列表投影出如下 `Presence` 边：

```text
ControlFlags2 -> Velocity
ControlFlags2 -> MountType
ControlFlags3 -> PotionOfReturnOriginalUsePosition
ControlFlags3 -> PotionOfReturnHomePosition
ControlFlags4 -> NetCameraTarget
```

这正是图应当承担的粒度：先读控制字节，再决定目标字段是否出现。具体 bit（2、7、6、6、5）由字段条件 `PacketFlagBitCondition` 保存并执行，并投影为 `PacketEdge.SourceBitIndex`，因此图也不会丢失该阅读信息。`PacketLayout` 从同一份声明按字段顺序生成写入、读取和“flag 与 nullable 字段存在性一致”的结构校验；它还拒绝错误 message id 与未完全消费的字节。概念实现仍未接入正式 `PacketFramework`，因此不会悄悄改变现有 Packet 13 的读写实现。

## 取舍

- 保留 QuikGraph 的 `AdjacencyGraph` 作为内部图存储，避免手写邻接表基础设施。
- 删除 `PacketRelation`：它只是 `PacketEdge` 的重复载体，没有独立行为。
- 删除构建后 `AddNode` / `AddDependency` 入口：定义一旦用于 codec，不应再被悄悄修改。
- 不新增 rule、visitor、builder、condition 接口或抽象父类。

## 验收

独立验证程序应证明：

1. 可直接构造 `ControlFlags2 -> Velocity (Presence)`；
2. `Nodes` 保持输入的声明顺序，`Dependencies` 暴露完整的有类型边；
3. 未注册端点和环会在定义构造时被拒绝；
4. 旧的 `PacketRelation` 与 `IPacketRelation` 不再存在；
5. `Prototypes/graph-layout-codegen/GraphVerification.csproj` 与其 Graph exporter/bootstrap 入口均能编译运行；仓库根 `NetWork.csproj` 已移除。
