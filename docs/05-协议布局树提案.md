# 实例化协议图重构提案

> 状态：历史的扩展性草案。当前实现起点以 [06-有向依赖图初步提案](./06-有向依赖图初步提案.md) 为准；不要将本文的实例、表达式与布局节点视为已批准的首阶段模型。

## 决策

不再把 `PacketFramework` 的扁平字段定义扩展成更大的 builder，也不以“布局树 + 三套独立 plan”作为中心模型。新的中心是：

> 一份不可变的 `PacketBlueprint` 描述协议；每次读、写或校验创建一个独立的 `PacketInstance`；同一份已解析的实例图驱动读、写、校验与可读诊断。

该设计直接继承 `PacketFrameworkConcept` 的原始意图：包负责调度、字段负责自身 codec、条件明确引用前序字段、包实例可描述当前活跃路径。但它移除概念稿中造成复杂度失控的实现方式：schema 持有字段值、所有结构退化为一维 field list、条件是不可见 lambda、复杂包只能整体 `CustomCodec`。

## 保留与舍弃

| 原概念 | 保留方式 | 舍弃原因 |
|---|---|---|
| 字段拥有类型、值与读写能力 | `Atom<T>` 持有 codec；值落在 `PacketInstance` 的 slot | blueprint 必须并发安全、可复用 |
| 包统一调度 | `PacketBlueprint.Resolve` 统一生成实例图 | 不再直接遍历扁平字段数组 |
| 条件显式声明依赖 | `ProtocolExpression` 引用 `SlotRef<T>` | `Func<...>` 不可显示、不可验证 |
| `Describe()` 展示动态位置 | `PacketInstance.Describe()` 输出树、wire span、值状态与决策 | 不再只显示活跃字段索引 |
| 固定/可变字段分类 | 删除 `PacketFieldKind` 作为执行分类 | “是否存在”属于 `Gate`，不是字段固有属性 |
| 全包 `CustomCodec` | 删除 | 会切断统一读、写、校验和诊断 |

## 核心对象

### `PacketBlueprint`

不可变、可注册、无状态的协议定义。它只描述 message id、根节点、slot 定义、版本 profile、预算和实例映射器。`PacketBlueprint` 不能保存任何单包字段值，也不能访问 `Main`、会话或可变游戏对象。

### `PacketInstance`

一次读、写或校验的协议状态。它包含：

- `PacketBlueprint` 的引用。
- 按作用域保存的 typed slot 值、存在状态和来源。
- 已解析节点、wire 起止偏移、判断结果和错误路径。
- 只读 `ProtocolContext` 与 `LayoutBudget`。

它替代 `ConceptPacketSchema` 中可变字段值。一次解码失败时丢弃 instance，不会污染下次读取；同一 blueprint 可并发创建任意多个 instance。

### `SlotRef<T>` 与 `ProtocolExpression`

`SlotRef<T>` 是字段的稳定身份，不使用字符串查找。表达式是可显示的 AST，只引用当前或父作用域中已发布的 slot：

```text
Flag(controlFlags2, HasVelocity)
Equals(mode, Teleport)
And(Exists(playerId), InRange(width, 1, 200))
Catalog(tileType, RequiresFrame)
```

构建时拒绝未知 slot、后序 slot、跨作用域非法引用和循环依赖。运行时表达式只从 instance 读取值，不能访问 DTO 或全局状态。确有必要的扩展规则只能使用具名 `ContextPredicate`，并声明所需 `ProtocolContext` 目录与 revision。

### `ProtocolAtom<T>`

原概念中 `ConceptPacketField<T>` 的替代品。它定义 wire 类型、对称 codec、默认值、范围规则和显示名；读取时向 slot 写入值，写入时从 slot 取值，校验时校验同一个 slot。复杂领域值通过具名 `ProtocolAtom<T>` 实现，不允许匿名的整包读写 delegate。

## 少数节点，不扩张 DSL

整个协议图只需要六种节点。其他结构必须由它们组合，而不是新增“某某包专用节点”。

| 节点 | 责任 | 典型组合 |
|---|---|---|
| `Atom` | 读、写、校验一个 slot | 整数、字符串、Bits、Guid、命名领域 codec |
| `Block` | 以声明顺序组织子节点并建立作用域 | 包 body、语义 section、嵌套结构 |
| `Gate` | 条件成立时解析一个子节点 | optional 字段、共同存在字段组 |
| `Select` | 根据已读 selector 选择唯一分支 | variant、变宽整数、判别 payload |
| `Loop` | 在受限边界内重复一个子节点 | 固定数组、count 数组、矩形、哨兵序列 |
| `Transform` | 为一个有界子 block 建立转换流 | Deflate、加密、长度限定 segment |

`Bits` 是带命名位和规则的 `Atom`；`AllOf` 是 `Gate(Block)`；固定数组是 `Loop(Exactly(n))`；RLE 是带 instance 状态的 `Loop`；嵌入子协议是 `Atom` 或 `Block`；尾随表是根 block 中显式排在正文之后的 `Loop`。这避免模型随着 Terraria 的历史特例无限膨胀。

## 统一的解析模型

`Resolve` 不是预先生成三套互不关联的计划，而是在一个 instance 内建立真实的解析图。每个节点解析后得到 `ResolvedNode`：名称、路径、状态、依赖结果、wire span、子节点和错误。

### 解码

```text
Frame body -> new PacketInstance
           -> Resolve(root, Decode)
           -> StructuralValidate(instance)
           -> Materialize DTO
           -> 显式 Apply
```

`Atom` 成功读取后立即发布 slot；后续 `Gate`、`Select` 和 `Loop` 只能看到已经发布的前序值。`Block` 完成后必须完全消费自己的有界输入。任何失败都保留 resolved trace，但不 materialize 或 apply 半成品。

### 编码

```text
DTO -> PacketProjector -> PacketInstance
    -> Prepare(instance) -> Resolve(root, Encode)
    -> StructuralValidate(instance) -> Write resolved graph
```

`PacketProjector` 只把 DTO 值放入 slot；`Prepare` 是纯函数，可计算控制位、默认值和 variant，但不能写入传输缓冲或改变业务状态。解析完成后，写入器只按 resolved graph 的线序写出 active atom，确保编码使用与解码相同的条件、分支和循环边界。

### 校验

校验不另写一套逻辑。它检查已解析图的以下事实：

- 每个 active atom 有合法值，inactive atom 没有不允许的值。
- 每个 `Gate` 的存在性与条件一致。
- `Select` 有且仅有一个合法分支。
- `Loop` 的实际项数、RLE 展开数或 grid 面积符合边界。
- `Transform` 子流完全消费且未超预算。
- 引用、目录 predicate 和跨 slot 约束全部成立。

## 作用域和大包状态

复杂性不通过全局字段或 closure 保存，而通过 instance scope 显式保存。

- `Block` 创建命名子作用域；重复项有独立 item scope，因此 `item[i].type` 和 `item[j].type` 不会冲突。
- `Loop` 的索引、剩余项数和临时状态是 instance slot，例如 `grid.previousTile`、`grid.pendingRun`。
- `Loop` 的边界必须是 `Exactly`、`Count(slot)`、`Until(predicate)` 或 `Area(widthSlot, heightSlot)` 之一，并声明最大值。
- `Transform` 创建有界子 reader/writer；子 scope 的成功不等于父 scope 成功，必须完成完整消费和预算检查。

这使 TileSection 可以直接表达为“Deflate 下的 area loop，loop state 为 previous tile 与 pending run，之后三个普通尾表”，而无需把 RLE、收集表和世界写入藏在 custom codec 中。

## 可读性是第一产物

每个 blueprint 必须自动产生两种视图：

1. `DescribeBlueprint()`：静态树，显示线序、slot、表达式依赖、版本 profile、边界和 codec。
2. `DescribeInstance()`：动态树，显示条件真值、选择的分支、循环次数、wire offset、值是否存在及失败点。

Packet 13 的正确 wire order 应展示为：

```text
PlayerId
ControlFlags1
ControlFlags2
ControlFlags3
ControlFlags4
SelectedItem
Position
When(ControlFlags2.HasVelocity) -> Velocity
When(ControlFlags2.HasMount) -> MountType
When(ControlFlags3.HasPotionOfReturn) -> Block(OriginalUsePosition, HomePosition)
When(ControlFlags4.HasNetCameraTarget) -> NetCameraTarget
```

它保留原概念“可看到当前到底读了什么”的优点，也修正当前概念规格与目标 Terraria wire order 不一致的问题。

## 代表性声明外观

以下为目标外观，不是本次实现代码。字段句柄是 slot 引用，结构由 block/gate/loop 表达：

```csharp
var packet = PacketBlueprint.Define(PacketType.PlayerControls, root =>
{
    var playerId = root.U8("PlayerId");
    var flags1 = root.Bits("ControlFlags1", PlayerFlags1.Definition);
    var flags2 = root.Bits("ControlFlags2", PlayerFlags2.Definition);
    var flags3 = root.Bits("ControlFlags3", PlayerFlags3.Definition);
    var flags4 = root.Bits("ControlFlags4", PlayerFlags4.Definition);

    root.U8("SelectedItem");
    root.Vector2("Position");
    root.When(Flag(flags2, "HasVelocity"), body => body.Vector2("Velocity"));
    root.When(Flag(flags2, "HasMount"), body => body.U16("MountType"));
    root.When(Flag(flags3, "HasPotionOfReturn"), body => body.Block("PotionOfReturn", group =>
    {
        group.Vector2("OriginalUsePosition");
        group.Vector2("HomePosition");
    }));
    root.When(Flag(flags4, "HasNetCameraTarget"), body => body.Vector2("NetCameraTarget"));
});
```

没有 `PacketFieldKind.Variable`、`HasValue` lambda、组名字符串或整包 custom codec。结构本身就是可读模型。

## 协议上下文与业务边界

`ProtocolContext` 是 instance 的只读输入：协商版本、capability、Tile/NPC/Projectile 的版本化目录和资源预算。它可回答“此 tile type 是否需要 frame”，但不能回答“当前玩家是否有权限”或修改世界。

以下职责严格在 blueprint 外：

| 职责 | 所属层 |
|---|---|
| 长度前缀、收包缓冲、回填长度 | `MessageFrame` / 传输适配 |
| message id 分派 | `PacketCatalog` |
| DTO 到 slot 的投影、纯默认化与 variant 选择 | `PacketProjector` / `Prepare` |
| 会话状态、身份重写、权限与反滥用 | `SessionGate` / 入站 policy |
| DTO 写入世界、缓存更新、连接状态推进 | handler 的显式 `Apply` |
| 接收者过滤、复制计数与投递状态 | `ReplicationPolicy` |

因此同一 `PacketBlueprint` 可以用于客户端、服务端、离线 wire verifier 和文档生成，不会把 `NetMessage` / `MessageBuffer` 的副作用重新引入协议层。

## 安全和失败模型

每个 instance 持有不可绕过的 `LayoutBudget`：最大输入/输出字节、解压后字节、压缩比、嵌套深度、字符串字节、循环项数、grid cell 数和 RLE run 长度。乘积、计数和偏移均使用 checked 运算。

错误统一为 `ProtocolFault`，至少包含 message id、blueprint revision、node path、wire offset、期待/实际、表达式结果和触发的预算。错误携带 trace，但不泄露或持久化未验证的领域状态。

## 对现有代码的迁移

### Phase 0: 固定基线

- 以真实 Terraria wire 为 Packet 13、WorldData、NPC/Projectile 和 TileSection 建立 golden fixture。
- 明确修复或隔离当前 Packet 13 的线序差异。
- 为概念稿补足条件、错误依赖、完整消费和并发 instance 测试。

**门槛：** 真实字节、截断、额外字节、错误 selector 和后序依赖均有可重复测试。

### Phase 1: 实例内核

- 实现 `PacketBlueprint`、`PacketInstance`、`SlotRef<T>`、`ProtocolAtom<T>`、表达式 AST、`Block` 和 `Gate`。
- 用 Packet 13 验证一次 resolved graph 同时驱动读、写、校验与 `DescribeInstance()`。
- 保留 `PacketDefinitionRegistry` 作为 catalog 入口，不改动会话管线。

**门槛：** blueprint 不含可变值；两个并发 instance 不共享状态；Packet 13 的静态与动态描述均可由测试断言。

### Phase 2: 选择和重复

- 加入 `Select`、`Loop`、scope、`ProtocolContext` 和预算。
- 迁移 WorldData 的固定数组、命名 bitset、Guid 和嵌入值；迁移一个变宽实体快照。

**门槛：** loop、selector、固定数组和目录 predicate 都有对称读写、超限和诊断测试；没有整包 custom codec。

### Phase 3: 变换和有状态 grid

- 加入 `Transform` 与 stateful `Loop`，用 TileSection 验证 Deflate、RLE、二维边界和尾表。
- tail table 只生成 DTO 引用，由 handler 在解码提交后应用。

**门槛：** RLE 展开数精确等于面积；所有子流完全消费；恶意尺寸、run 和解压缩比都在写入世界前被拒绝。

### Phase 4: 兼容层收敛

- 让简单的 `PacketDefinitionBuilder` 成为 blueprint 的薄 facade，或按使用结果废弃。
- `ConceptPacketSourceAttribute` 可在此阶段生成 blueprint 声明和 DTO projector；它不是运行时事实来源。
- 清点并删除整包 `IPacketCustomCodec`。

**门槛：** 任何剩余自定义逻辑都只是具名 `ProtocolAtom` 或显式应用层，且有边界、revision 和测试说明。

## 风险与拒绝项

- 不自动从现有 lambda 推导表达式；必须手工迁移为可读 AST，避免错误声称可分析。
- 不让 source generator 隐藏 wire order；生成结果必须能导出同样的 blueprint 描述。
- 不把“语义上相邻”当成“wire 上相邻”；所有 block 都保留声明线序。
- 不让 `Apply` 回写 instance 或影响编码；读、写和业务状态保持单向边界。
- 不对历史 `MessageBuffer` 的残缺 case 覆盖面做无依据的兼容承诺；只以 golden wire fixture 作为协议事实。
