THROWAWAY LOGIC PROTOTYPE · test4

Slot-DAG 协议编译器

这个原型只回答一个问题：字段不再持有 DAG，而由可扩展的插槽持有依赖关系，能否编译成可读的线性写入计划和读取计划，同时保留旧协议的线序、条件字段和重复作用域？

先看这条原则
依赖图决定“谁必须先准备好”；
WireSequence 决定“字节按什么顺序出现”。
两者不能混为一个拓扑序。
原型边界：这里的 Packet 13、Packet 20 和 Packet 10 是计划生成的概念验证。Packet 10 只模拟 Transform、RLE 状态和 side table 的布局，不实现 Terraria 正式 Deflate/RLE codec；本页没有测试代码，也不会改动生产协议。

模型分层
两个来源，三个运行态

          
Lower PacketSchema
  packet id / fields / wire type / declared wire order

Upper SlotGraph
  slot / kind / dependency / presence / shape / scope

Compiler IR
  validated DAG + explicit WireSequence + scope templates

Runtime
  Snapshot -> PresencePlan -> LayoutRecords -> byte[]
  byte[] -> FixedReader -> wire flags -> DecodePlan -> values

        

        

          
代数数据类型式 SlotValue

          
SlotValue
  = U8(byte)
  | U16(ushort)
  | I32(int)
  | F32(float)
  | Vec2(x, y)
  | Bits8(byte)
  | Bytes(byte[])
  | Struct(SlotValue[])
  | Sequence(SlotValue[])
  | Variant(tag, SlotValue)
  | Absent

          
建议只让编译器 IR 和 codec seam 使用 SlotValue；领域 DTO 仍然可以保持强类型，避免把业务对象变成反射字典。

        

      

      

        

          
静态检查规则
编译期应该拒绝

          

            
1slot id 重复或依赖目标不存在

            
2dependency 子图成环

            
3Conditional 没有稳定 presence slot

            
4gate 在 wire order 之后才被读取

            
5PresenceGroup 只出现部分成员

            
6重复 scope 没有 local mask

            
7MaxBytes 小于最小编码长度

            
8loop 没有 count / sentinel / max bound

          

        

        

          
兼容 PacketFramework 的 seam

          
PacketDefinitionRegistry
  -> PresenceAwareCodecAdapter
      -> PacketSnapshot / Context
      -> Compiled EncodePlan / DecodePlan
      -> existing PacketCodec result

Existing framework keeps:
  message-id registration
  MessageFrame / NetMessage
  codec entry and error propagation

New upper framework owns:
  SlotGraph / PresencePlan / layout records
  field encoder and reader plan
